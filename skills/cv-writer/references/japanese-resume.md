# 日本の職務経歴書

## セクションの順序

```
職務経歴書                                   YYYY年MM月DD日現在 / 氏名：〇〇 〇〇  ← 右寄せ

1. 職務要約                  200〜300字
2. 活かせる経験・知識・技術   箇条書き3〜5点
3. 職務経歴                  本体。逆編年式
4. スキル・専門性            職種に応じた表
5. 保有資格・語学
6. 社外活動・アウトプット     実績が無ければセクションごと削除
7. 自己PR                    300〜500字
                                                                          以上  ← 右寄せ
```

順序の理由:

- **職務要約が最初。** 採用担当は1枚目の上部だけで一次通過を判断する。ここに具体性が無い書類は先を読まれない。
- **「活かせる経験」を職務経歴より前に置く。** 詳細な職務経歴（長い）を読む前に「この人はどの領域の人か」を3行で伝えられる。後段のスキル表とは役割が違う（要約 vs 網羅）ので、粒度を変えて両方置いてよい。
- **スキル表は職務経歴の後。** 表を前に置くと「何ができるかは書いてあるが、何をした人か分からない」書類になる。文脈（職務経歴）→ 索引（表）の順が読みやすい。
- **自己PRは末尾。** 冒頭に置くのは英文レジュメの発想で、和文では浮く。

**末尾の「以上」（右寄せ）は和文ビジネス文書の作法。** 省くと体裁を知らない人に見える。細部だが実際に効く。

## 職務要約

200〜300字、3〜4文。400字を超えたらそれは要約ではない。

構成の型:

1. 通算年数 + 主戦場（領域 + 担当レイヤ）
2. 現職での役割と扱っている規模 — **数値を必ず1つ入れる**
3. 代表的な成果を1つ、数値付きで
4. 強み、または今後活かしたい方向を1文

**禁止語:**「幅広く」「様々な」「一通り」「各種」。情報量がゼロで、書類選考で最も嫌われる語彙。これらを使いたくなったら、具体例を1つ挙げるべき箇所である。

## 職務経歴の形式

| 形式 | 並び | 向く人 | 弱点 |
|---|---|---|---|
| 編年式 | 古い→新しい | 新卒〜第二新卒、成長曲線を見せたい人 | 読み手が最も知りたい直近の情報が末尾に来る |
| 逆編年式 | 新しい→古い | 中途採用のほぼ全員 | 昔の経験が薄く見える（意図的にそうするので実質問題なし） |
| キャリア式 | 時系列を崩し領域別に束ねる | 案件数が20超、または大きな職種転換 | 在籍期間が追えず「何か隠している」と読まれやすい |

**原則として逆編年式を採る。** 中途採用の一次判断は「直近2〜3年で何をどの規模でやっていたか」に強く偏るため、それを1枚目に置ける形式が要る。

ただし単純な逆編年にせず、**冒頭に職務経歴サマリ表**（期間 / 企業 or 案件 / 役割 / 主な技術・領域）を4〜6行で置く。これでキャリア式の利点（一望性）を取り込みつつ、時系列が追えない弱点を構造的に潰せる。

在籍1社なら、サマリ表は会社単位ではなく**案件・フェーズ単位**にする。

## 会社ブロックと詳述エントリ

会社ごとに「会社概要表 → 詳述エントリ（2ページなら3件、3ページなら4〜5件）」の入れ子にする。**詳述の単位は職種で変わる**（案件・担当領域・役割の変遷・組織・テーマ）。SKILL.md の Stage 2 を参照。会社概要を書くのは和文の作法で、採用側が転職元の規模感を測るために見ている。

```markdown
### 株式会社〇〇（2021年4月 - 現在）

| 項目 | 内容 |
|---|---|
| 事業内容 | |
| 従業員数 | |
| 雇用形態 | |

#### 担当した仕事の名称（2024/04 - 2025/03）

| 役割 | チーム規模 | 担当範囲 | 技術・手法 |
|---|---|---|---|
| | | | |

**概要**
何が課題だったか / 何を求められていたか。3行程度。

**担当業務**
- 動詞で終わる箇条書きを4〜6個。主語は「チーム」ではなく「自分」

**成果**
- 担当業務とは分けて書き、必ず数値を含める
```

設計の意図:

- **役割・規模・技術は表にする。** 読み手はここを拾い読みする。散文に埋めると見つけられない。
- **担当業務は動詞で終える。**「〜の対応」「〜業務」のような名詞止めは、何をしたのかが伝わらない。ただし営業のように担当業務が誰でも同じ言葉になる職種では、ここを2〜3行に圧縮して成果側に紙面を寄せる。
- **成果を担当業務から分離する。** 混ぜると成果が埋もれる。日本の実務者の職務経歴書で最も欠けているのがこの分離。

会社概要の「従業員数」などは、確かな数字が無ければ**行ごと削る**。プレースホルダーや推測値を残すより良い。

## スキル表

経験年数だけの表は情報として弱い。触っただけの3年と、判断をしてきた3年が同じに見えてしまう。**年数 + レベル + 具体的な用途**の3列にする。

```markdown
**レベル定義**　A: 設計判断・選定ができ指導・レビューが可能／B: 一人称で完遂できる／C: 指示のもとで経験あり

| 技術・領域 | 経験年数 | レベル | 主な用途 |
```

カテゴリは4〜5個、合計20〜25行が上限。**触っただけのものを全部書くと、本当に強い項目が埋もれて逆効果になる。**

レベルは**こちらが案を提示して確認を取る**。ゼロから自己申告させるより速く、かつ過小評価に対して「ここは上でよいのでは」と提案できる。ただし本人が下げると言ったら下げる。面接で崩れるほうが損失が大きい。

## 資格

取得年月 + 正式名称。順序は取得順ではなく**応募先との関連度が高い順**。上位資格を持っているなら下位は省いてよい。

該当が無ければ**セクションごと削除**する。「特になし」と書くと、空欄の存在自体がマイナスに見える。

学習中のものは「（2026年〇月受験予定）」と書いてよい。

## 自己PR

300〜500字。見出し付きで2ブロックが読みやすい。

「協調性があります」「責任感が強いです」型の性格アピールは書かない。**行動と結果で人柄を示す。** 何が起きていて、何を考えて、どう動いて、結果どうなったか、の順で書く。

## 履歴書との関係

履歴書は職務経歴書とは別の書類で、**学歴・職歴・資格を定型の枠に埋める形式書類**である。市販の様式、Web配布の様式、応募先指定の様式のいずれかを使うのが普通で、Markdown から生成するものではない。

このスキルでやるのは次の2つ。

1. **職務経歴書を先に完成させ、在籍期間・社名・役職をそちらの正とする**
2. **履歴書に転記する事項を一覧で渡す** — 学歴、職歴（入退社年月と正式な社名）、資格の正式名称と取得年月

**両者の齟齬は経歴詐称の疑義になる。** 1文字でも違わないよう、転記用の一覧を作るところまでが仕事。西暦と和暦のどちらで書くかも揃える。

履歴書に書いて職務経歴書に書かないもの: 生年月日、住所、顔写真、通勤時間、扶養家族、志望動機。逆に職務経歴書の詳細な実績は履歴書には書かない。

## 表記の約束

- 文体は「です・ます」調に統一。箇条書きの語尾は体言止めか動詞終止形のどちらかに揃える
- 数字・英字は半角。年は西暦（**履歴書と表記を揃えること**）
- 句読点は「、」「。」に統一。「，．」を混ぜない
- 見出しに連番を振る。面接で「3番の2つ目の案件ですが」と参照される場面が実際にある

## よくある落とし穴（重い順）

1. 成果が無く、担当業務の羅列で終わる
2. 主語が「チーム」で、本人の貢献が特定できない
3. 技術・スキルの羅列だけで深さが伝わらない（器用貧乏に見える）
4. 規模の記述が無い
5. 応募先を問わず同じ1本を使い回す
6. 長すぎる（4枚以上）
7. 職務要約が抽象語だらけ
8. **空白期間を無説明で放置する** — 3か月以上の空白は必ず一行で説明する。隠すと面接で必ず突かれ、印象が悪化する
9. **履歴書との齟齬** — 在籍期間・社名・役職が1文字でも違うと経歴詐称の疑義になる。**職務経歴書を先に完成させ、履歴書をそれに合わせる**運用にする
10. 謙遜しすぎ、または盛りすぎ。「補助的に関わりました」は書く価値が無いので削る。逆にやっていないことを「設計から担当」と書くと面接で崩壊する

## 技術名・固有名詞の誤記

専門職の書類では、固有名詞の誤記がそのまま能力の疑義になる。`scripts/lint.mjs` が主要なものを検出するが、職種に応じて追加すること。

例: `Github → GitHub` / `Javascript → JavaScript` / `MySql → MySQL` / `Node.JS → Node.js` / `Kubernates → Kubernetes` / `Rest API → REST API`
