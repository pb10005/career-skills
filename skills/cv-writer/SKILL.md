# 職務経歴書・レジュメの作成

## このスキルが解こうとしている問題

応募書類で落ちる原因のほとんどは、経歴が乏しいことではなく**書き方**にある。とりわけ多いのが次の4つで、いずれも本人には見えにくい。

1. **担当業務の羅列で終わり、成果がない。**「〜を担当」が10行並ぶ書類は、読み手にとって差別化の材料がゼロになる。
2. **主語が「チーム」で、本人の貢献が特定できない。** 採用側が知りたいのは「この人個人に何ができるか」だけである。
3. **規模が書かれていない。**「システムを開発」「新規開拓を担当」だけでは、扱っていた仕事の重さが分からない。
4. **数値はあるが、再現性が伝わらない。** 営業や企画で起きやすい。「達成率130%」と書いてあっても、**どうやって達成したのか**が無いと、実力なのか市況や引き継いだ顧客のおかげなのか読み手に判断できない。

このスキルの中心は、これらを**ヒアリングの設計によって構造的に潰す**ことにある。フォーマットを整えるのは副次的な仕事にすぎない。

## 進め方の全体像

```
Stage 0  前提を決める（書類の種類・言語・分量・個人情報の扱い）
Stage 1  骨組みを作って見せる      ← ここで一度、形を見てもらう
Stage 2  経歴の骨格（区切りの単位を決め、詳述する塊を選ぶ）
Stage 3  塊ごとの事実（役割・規模・担当範囲・使ったもの・課題）
Stage 4  定量化プローブ            ← このスキルの核心
Stage 5  スキル・資格の棚卸し
Stage 6  職務要約と自己PR          ← 必ず最後に書く
Stage 7  仕上げ（分量調整・表記統一・PDF）
```

各ステージの終わりで**必ずファイルに書き込み、その時点で完結した文書の状態を保つ**。ユーザーが途中で離脱しても価値が残り、こちらも次の質問の精度を上げられる。

### 質問の出し方

一度に30問ぶつけない。**1ラウンドあたり4問まで**に抑え、選択式で答えられるものは選択式にする。社名・エピソード・成果の中身のように選択肢を列挙できないものは、無理に選択式にせず自由記述で聞く。

選択肢には「なぜその選択肢を選ぶと書類がどう変わるか」を添える。ユーザーは書類の作法を知らないことが多く、選択の帰結が見えないと答えられない。

**4問に収まらないときは2ラウンドに分ける。** 会話の中で既に分かっていること（経験年数、職種など）は質問から外す。

## Stage 0: 前提を決める

ここを飛ばすと後で全文の書き直しが発生する。最低限これだけは先に確定させる。会話から既に分かっているものは聞かない。

- **書類の種類** — 日本の職務経歴書 / 英文レジュメ / 両方。履歴書も必要か
- **想定応募先** — 業界と企業タイプ、そしてプレイヤー職かマネジメント職か。強調すべき箇所が変わる
- **経験年数と社数** — 分量と、詳述する塊の数がここで決まる
- **個人情報の扱い** — 氏名・連絡先をファイルに書くか、プレースホルダーにするか
- **転職の軸** — 何を変えたいのか。職務要約と自己PRの方向がこれで決まる

書類形式ごとの構成・慣行は `references/japanese-resume.md` と `references/english-resume.md` に分けてある。**Stage 0 で種類が決まった時点で該当ファイルを読むこと。** 日本の職務経歴書と欧米式レジュメは、単なる翻訳ではなく構成の思想が違う。

**Stage 0 の質問より先に骨組みを出してよい。** 空欄のテンプレートを見せてから前提を聞くほうが、ユーザーは答えやすい。その場合は「暫定で置いています」と断り、Stage 0 の回答で組み替える。

## Stage 1: 骨組みを先に作って見せる

いきなり中身を聞き始めるより、**空欄とコメント付きのテンプレートを先に作って PDF にして見せる**ほうが速い。全体像が見えると、ユーザーは自分の経歴のどこを話せばよいか分かるようになり、以降のヒアリングが穴埋めに変わって心理的な負荷が下がる。

未入力箇所は `{{氏名}}` のようなプレースホルダーで残す。同梱のビルドスクリプトはこれを PDF 上で黄色くハイライトするので、埋め忘れたまま提出する事故を防げる。

この段階で**一度 PDF をビルドして目視する**。フォント崩れや文字化けは、内容を入れてから気づくと手戻りが大きい。

**この時点のページ数は気にしなくてよい。** 空のテンプレートは見出しと表の枠だけで場所を食うため、実際の文章より膨らむ。分量の管理を始めるのは Stage 4 以降、本文が入ってからでよい。

### 作業ディレクトリ

**ユーザーの既存リポジトリの中に勝手に作らない。** 個人情報を扱ううえ、既存の `.gitignore` を書き換えることになる。専用のディレクトリを作るか、どこに作るかをユーザーに確認する。既存の CV リポジトリがあるならその作法に従う。

## Stage 2: 区切りの単位を決める

**職務経歴を何で区切るかは職種によって違う。** ここを間違えると、以降の全部が噛み合わなくなる。

| 区切りの単位 | 向く職種・状況 |
|---|---|
| プロジェクト・案件 | 受託開発、SI、コンサル、制作。案件ごとに体制と期間が変わる仕事 |
| 担当領域・担当製品 | 営業、マーケティング、企画。担当する市場・商材・顧客層で区切る |
| 役割・フェーズの変遷 | 在籍が長く、同じ仕事を続けている場合。メンバー期 → リーダー期など |
| 組織・部署 | 社内異動が多い場合。バックオフィス、企画系に多い |
| テーマ・研究領域 | 研究職、専門職 |

**営業で「案件」ごとに書くと個別商談の羅列になる。** 担当領域（業界・商材・顧客規模）か、役割の変遷で区切る。同様に、バックオフィスや企画職を無理にプロジェクト単位に押し込まない。

区切りを決めたら、**そのうち詳述するものを絞る。**「関わったものを思いつく限り挙げてください」と依頼したうえで、載せるのは3〜4件、残りは一覧表に1行ずつ落とす。この選定を先にやらないと、全部を薄く書いた散漫な書類になる。

### プレイングマネージャーの扱い

個人実績とチーム実績を同じ塊に混ぜると、数字が二重に見えて読み手が混乱する。**役割で塊を分ける**のが最も読みやすい。

- メンバー期 → 個人の予算・実績・担当数
- リーダー期 → チームの人数・チーム全体の数字・育成した人数。個人実績は書くとしても補足に留める

応募先がマネジメント職ならリーダー期を厚く、プレイヤー職ならメンバー期を厚くする。**同じ経歴でも配分が変わる。**

## Stage 3: 事実を集める

各塊について押さえる項目。職種によって語彙を置き換える。

役割 / 規模（チーム人数・予算・担当社数・対象人数など）/ 担当範囲（工程・フェーズ・業務範囲）/ 使った技術・手法・ツール / **何が課題だったか**。

最後の「課題」が特に重要で、ここを書くと後段の成果が評価可能になる。「何をしたか」だけでは、それが難しいことだったのか誰でもできることだったのか読み手には分からない。

## Stage 4: 定量化プローブ（このスキルの核心）

**「成果を数値で教えてください」と聞いてはいけない。** ほぼ確実に「特に数値はないです」で終わる。人は自分の仕事を過小評価するし、そもそも成果を数値の形で記憶していない。

代わりに、**Before/After と規模に分解して**上から順に当て、答えが出たら止める。

1. **Before / After** — 最も成功率が高い。「その改善の**前**は何分／何件かかっていましたか。**後**はどうなりましたか」。時間・回数・件数・金額のどれでもよい。
2. **規模** — Before が無くても答えられる。「利用者数・取扱件数・データ量・予算規模・担当社数はどれくらいですか」。**成果が出てこない場合の代替にもなる最重要情報。**
3. **影響範囲** — 「その仕組みは何人が使うようになりましたか」「**あなたが提案しなかったら、それは起きていましたか**」。後者は本人の差分を抽出する問いで、最も強力。
4. **事業インパクト** — 「コストはいくら変わりましたか」「他部署の工数は減りましたか」。実務の成果を事業の言葉に翻訳する。
5. **定性フォールバック** — 「社内でどんな反応がありましたか」「そのやり方は横展開されましたか」。数値がどうしても無いときの受け皿。

各塊で**必ず1回は**次のどれかを当てる。過小評価を崩すのに効く。

- 「その仕事で、**あなたが居たから変わったこと**を1つ挙げるとしたら何ですか」
- 「一番『これは自分にしかできなかった』と思う部分はどこですか」
- 「想定外にうまくいかなかったことと、どう対処したかを教えてください」（失敗対処は成果として書けることが多く、しかも具体的に語りやすい）

### 数字が先に出てくる職種では、逆を聞く

営業・マーケティングなど、**数値が最初から出てくる職種では失敗の形が逆になる。** 「達成率130%」「売上2億」は書けるが、それだけでは実力か市況か引き継いだ顧客のおかげか区別できない。この場合に聞くのは**手段と再現性**である。

- 「その数字は、**何をしたから**達成できたのですか。前任者や同僚と違うことをしましたか」
- 「同じやり方を別の商材・別の顧客層でやっても再現できますか」
- 「チーム内での順位はどのくらいでしたか。母数は何人ですか」（**絶対値より相対順位のほうが強いことが多い**）
- 「その予算は、前年比でどれくらい伸びた目標でしたか」（達成率100%の重みは目標設定で全く変わる）
- 「新規で取った分と、既存顧客から積み上げた分の比率は」

数値と手段が揃って初めて「再現性のある人」に見える。**片方だけでは弱い。**

### 変換案はこちらが出す

ユーザーに成果を書かせるより、**こちらが変換案を提示して Yes/No と数値の確認だけを求める**ほうが精度が高く速い。

> ユーザー:「新規開拓を担当していました」
> こちら:「『未取引だった中堅製造業を対象に、年間◯社を新規開拓し、うち◯社を年間契約に転換。チーム内で新規獲得数1位（12名中）』のように書けます。社数と順位は合っていますか？」

### 数値が出ないとき

- 概算しか言えない → 「約」「およそ」を付ける
- 社外に出せない → **相対値化する**（「30%削減」「1/4に短縮」「数十万規模」）
- そもそも計測していない → 規模の記述に切り替える。規模だけでも仕事の重みは伝わる

**推測で数字を作らない。** 埋まらない項目はプレースホルダーのまま残し、ユーザーに確認する。書類の数字は面接で必ず掘られるため、盛った瞬間に破綻する。同じ理由で、実務経験のない技術や資格だけの領域をスキル表に載せてはいけない（資格欄に書くのは正しい）。

## Stage 5: スキル・資格の棚卸し

**Stage 3 で出てきたものをこちらが集約して提示し、確認と補完だけを求める。** ゼロから列挙させると漏れるし時間がかかる。

スキル表の形は職種で変える。**技術職の「経験年数 + レベル」をそのまま他職種に当てない。**

| 職種 | 表の列 | 理由 |
|---|---|---|
| 技術職 | 項目 / 経験年数 / レベル / 主な用途 | 技術ごとに触れた期間と深さが違う |
| 営業・企画 | 領域 / 実績・規模 / 具体的な内容 | **経験年数を書くと全部同じ年数になり情報量がゼロになる。** 「新規開拓：年間◯社、中堅製造業中心」のように実績で示す |
| 専門職・研究 | 領域 / 手法・ツール / 成果物 | 年数より、扱える手法と出したものが評価される |
| バックオフィス | 業務 / 対象規模 / 使用システム | 対象人数・拠点数・処理件数が効く |

レベル定義（A/B/C）は技術職向けの語彙である。他職種では無理に使わず、実績そのもので示す。

## Stage 6: 職務要約と自己PRは最後に書く

材料が全部揃ってから要約するほうが具体的になる。先に書くと抽象的な決意表明になり、書類で最も読まれる場所を無駄にする。

自己PRも「自己PRを書いてください」とは聞かない。**押したい軸を選ばせ、それを象徴するエピソードを聞き、こちらが構成する。**

## Stage 7: 仕上げ

- **分量を実測する。** 同梱の `scripts/build.mjs` はページ数を出力する。
- **表記ゆれを潰す。** `scripts/lint.mjs` が誤記・全角英数字・未入力箇所を検出する。辞書は `scripts/lint-dictionary.json` にあるので、**職種に応じて用語を追加する**（営業なら Salesforce、HubSpot、ARR など）。専門職の書類では固有名詞の誤記がそのまま能力の疑義になる。
- **文体を統一する。**「です・ます」と「である」を混ぜない。箇条書きの語尾を揃える。

## 分量の予算が構成を決める

分量は好みではなく制約として扱う。**先に予算を決めると、詳述する塊の数と1件あたりの字数が機械的に決まり、迷いが消える。**

日本の職務経歴書は A4 2枚が標準、3枚が実質的な上限（4枚以上は「まとめる力がない」と読まれる）。経験3年未満なら1〜2枚。

A4・9.5〜10.5pt・行間1.5〜1.75・余白15mm で **1ページあたり実効1,300〜1,450字**（実際の職務経歴書2本を実測した値）。表が多い構成ほど下限に寄る。

| セクション | 2ページ（約2,600字） | 3ページ（約3,900字） |
|---|---|---|
| 職務要約 | 250 | 250 |
| 活かせる経験 | 200 | 250 |
| 職務経歴 | 1,400 | 2,200 |
| スキル | 300 | 400 |
| 資格・社外活動 | 150 | 300 |
| 自己PR | 300 | 500 |
| 合計 | 2,600 | 3,900 |

職務経歴の予算から逆算すると、**2ページなら詳述3件（1件約450字）、3ページなら4〜5件**になる。会社概要表とサマリ表もこの予算に含まれる。

**経験8年以上で3件を詳述すると、2ページに収めるのは実際にはかなり厳しい。** 削って薄くするより3ページにするほうがよいことが多いので、無理に2ページへ押し込まない。3枚までは許容範囲である。

直近の塊に紙面の50〜60%を配分し、古いものは圧縮する。5年前の仕事を今の仕事と同じ分量で書くのは配分ミスである。

**担当業務の箇条書きは4〜6個が目安だが、職種で調整する。** 営業のように担当業務が誰でも同じ言葉（新規開拓・提案・クロージング）になる職種では、担当業務を2〜3行に圧縮して**成果側に紙面を寄せる**。定型文で行数を使っても差別化にならない。

溢れたときに削る順序は、古い塊の記述 → 担当業務の箇条書き → スキル表の低優先行 → 自己PRの2本目。

## 職種による重点の置き換え

構成の骨格は職種によらず同じで、**「何を数値で語るか」と「どの項目を前に出すか」だけが変わる**。以下は出発点であって、実際にはユーザーの職務内容に合わせて判断する。

| 職種 | 前に出す項目 | 主に使える数値 |
|---|---|---|
| ソフトウェア開発 | 技術スタック、設計判断の範囲、担当工程 | 規模（利用者数・トラフィック）、性能改善の前後、障害件数 |
| 受託開発・SI | 担当工程の幅、体制規模と立ち位置、顧客折衝 | 体制人数、ベンダー社数、予算・工数規模、納期遵守 |
| 営業 | 担当領域・顧客層・商材、役割の変遷 | 予算達成率と目標の伸び率、売上・粗利、新規/既存比、担当社数、単価、チーム内順位と母数 |
| 企画・マーケティング | 担当施策、扱った予算、意思決定の範囲 | CV率・CAC・LTV、予算規模、実施施策数と効果 |
| コンサルティング | 業界、テーマ、クライアント規模、役割 | プロジェクト規模、提言の実行率、削減額 |
| 人事・バックオフィス | 対象人数・拠点数、制度設計の範囲 | 処理件数、工数削減、離職率、採用人数と充足率 |
| 研究・専門職 | テーマ、手法、成果物の形 | 論文・特許数、被引用、実用化の有無、予算獲得額 |
| 管理職 | 組織規模、予算責任、採用・育成 | 人数、予算額、離職率、昇格者数 |

職種が変わっても**定量化プローブの構造は変わらない**。Before/After と規模を聞く、というやり方は営業にも研究職にもそのまま使える。

## 書かないもの

日本の職務経歴書では次を入れない。理由もあわせて伝えると納得されやすい。

- **志望動機** — 応募先ごとに変わるため、書類ではなくメール本文やエントリーシートの役割
- **顔写真・生年月日・住所** — 履歴書の項目であり、職務経歴書には不要
- **希望年収** — 書類段階で数字を出すと足切りされる。「面談時にご相談させてください」の一行に留める
- **空セクション** —「特になし」と書くくらいならセクションごと削り、その分量を職務経歴に回す

**顧客名・未公開のプロダクト名・社内システム名も原則書かない。**「大手金融機関向け」のように業種＋規模で表現する。ただし例外があり、**公開されている導入事例・受賞歴・プレスリリースに本人と社名が出ているものは書いてよい**。営業職では「どこに売ったか」が実績の中身であることが多いので、公開情報かどうかを本人に確認する。判断がつかないものは伏せる。

## 出力とビルド

`scripts/` に PDF 生成一式が入っている。Markdown を唯一のソースにして、Chromium の print-to-PDF で A4 の PDF を作る。pandoc も LaTeX も要らない。

```
scripts/build.mjs            Markdown → HTML → PDF。ページ数を出力。--png で確認用画像
scripts/lint.mjs             表記ゆれ・全角英数字・未入力プレースホルダーの検出
scripts/lint-dictionary.json lint の用語辞書。職種に応じて追記する
scripts/style.css            A4印刷用。日本語の禁則処理と CJK フォント指定を含む
assets/template-ja.md        職務経歴書の空テンプレート
assets/template-en.md        英文レジュメの空テンプレート
```

セットアップと既知の落とし穴（**日本語が中国語字形で出る事故**、段落内改行が PDF に半角アキを作る問題、Chromium がページ番号の CSS を実装していない件）は `references/build-setup.md` に書いてある。**PDF を作る前に必ず読むこと。** どれも黙って壊れるタイプの不具合で、出力を見ただけでは原因が分からない。

構造化データ（YAML/JSON）に分離してテンプレートで組む方式は、単一文書・単一言語なら**採らない**。Markdown を直接読める価値のほうが大きい（面接前日に読み返す、一文だけ直す、といった使い方が支配的なため）。日英2言語を同じ経歴から出し分けるなど、明確な多形式の要求があるときだけ検討する。

## 履歴書について

Stage 0 で「履歴書も必要」となった場合、**このスキルは履歴書そのものを生成しない。** 履歴書は学歴・職歴・資格を定型の枠に埋める形式書類で、市販・Web配布の様式や応募先指定の様式を使うのが普通だからである。

このスキルがやるのは次の2つ。

1. **職務経歴書を先に完成させる。** 在籍期間・社名・役職はそちらを正とする
2. **履歴書に転記すべき事項を一覧で渡す。** 学歴、職歴（入退社年月と正式な社名）、資格の正式名称と取得年月

**両者の齟齬は経歴詐称の疑義になる。** 1文字でも違わないよう、転記用の一覧を作って渡すところまでが仕事である。

## やってはいけないこと

- **経歴を創作しない。** 埋まっていない項目は TODO とプレースホルダーで残し、ユーザーに確認する。
- **ユーザーが決めた方針を黙って上書きしない。** 構成上の懸念があれば一度伝え、それでも本人が選ぶならその方針で完成させる。
- **本文が入った後は、分量オーバーを放置しない。** ページ数を実測して報告する。
